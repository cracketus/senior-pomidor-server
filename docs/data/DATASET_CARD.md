# Senior Pomidor Dataset Card

Status: public-data and research-dataset policy  
Last reviewed: 2026-09-03

## Purpose

Senior Pomidor collects and derives data to evaluate an embodied-AI pipeline operating on a real biological process. The long-term research record is intended to connect observations with reconstructed state, context, predictions, decisions/actions, safety constraints, and observed outcomes.

This document describes how Senior Pomidor data should be interpreted and published. It covers the current public sample and future sanitized research releases; it does **not** make private runtime storage public by default.

## Current public sample

A minimal reviewer-oriented sample is maintained under [`../../data/public-sample/`](../../data/public-sample/).

The current sample is **fully synthetic**. It follows selected current contracts/runtime shapes but contains no production observations and must not be cited as an experimental result.

Current sample modalities:

- reduced edge telemetry shaped as `senior-pomidor.edge.telemetry.v2`;
- photo metadata shaped as `senior-pomidor.edge.photo.v1`, with no image included;
- canonical state shaped as current `state_v1` output;
- environmental anomaly shaped as current `anomaly_v1` output.

The production plant-vision observation contract remains roadmap work in [#201](https://github.com/cracketus/senior-pomidor-server/issues/201); the public sample does not invent or freeze that contract early.

## Data sources

Depending on a future release, Senior Pomidor datasets may contain:

1. **Physical sensor observations** — air temperature/humidity, root-zone moisture/temperature, light, leaf-temperature proxies, and device/edge health from documented hardware boundaries.
2. **Photo metadata and reviewed imagery** — capture metadata and, only after explicit review, selected plant images.
3. **Derived environmental/state values** — for example VPD, canonical `state_vN`, confidence/quality fields, and anomaly outputs generated by documented deterministic or versioned processing.
4. **Context data** — weather, drought, radiation, agronomic, phenology, or other external context with source/version/provenance where licensing permits redistribution.
5. **Model-generated observations/hypotheses** — future VLM/LLM outputs with model/workflow/run provenance and explicit non-diagnostic status.
6. **Human-reviewed observations** — annotations or reviews attributable to a person/process, while preserving the distinction between visual review and validated biological diagnosis.
7. **Action/outcome data** — future candidate/actions, Guardrail decisions, execution records, manual interventions, and measured follow-up outcomes when the closed loop is implemented and validated.

Not every release will contain every modality.

## Temporal and geographic context

The first physical benchmark environment is tomato cultivation in Vienna, Austria. Public releases should use only the geographic and temporal precision required for scientific interpretation.

Exact private deployment addresses, private network/infrastructure details, or unnecessarily precise location metadata are not part of the public dataset boundary. Exact timestamps may also be reduced or shifted when they create a privacy/security risk and are not scientifically necessary; any transformation must be documented.

## Evidence and label taxonomy

Senior Pomidor uses provenance labels so that evidence does not become stronger merely through repeated processing or model summarization.

| Label | Meaning | Example |
|---|---|---|
| `measured` | Recorded by a named sensor/instrument boundary with unit/timestamp semantics | air temperature from a documented sensor |
| `observed` | Human or reviewed image observation with context | visible yellowing noted on a reviewed image |
| `derived` / `inferred` | Computed from documented inputs/method | VPD or canonical state field |
| `model_generated` | Produced by an LLM/VLM/ML workflow | “visible pattern is compatible with several stress hypotheses” |
| `human_reviewed` | A human reviewed/accepted/rejected a prior observation or model output | reviewer agrees that yellowing is visible |
| `synthetic` | Constructed for fixtures, simulation, examples, or tests | records under `data/public-sample/` as of 2026-09-03 |

`human_reviewed` does **not** automatically mean laboratory-confirmed disease diagnosis. Review provenance and the evidentiary method still matter.

When possible, releases should preserve the original evidence type plus processing/review provenance rather than replacing it with a single ambiguous `label` field.

## Public / private / synthetic split

### Private by default

- raw production telemetry payloads and database exports;
- unreviewed photos and photo EXIF/background content;
- raw private AI-analysis logs;
- exact private location/network/infrastructure information;
- secrets, credentials, host paths, logs, stack traces, process/service identifiers;
- partner data unless an explicit publication agreement permits release.

### Potentially publishable after review

- sanitized/aggregated telemetry;
- derived state/anomaly records with unnecessary identifiers removed;
- reviewed plant images with sensitive metadata/background handled;
- experiment/replay fixtures;
- action-response records that pass safety/privacy/partner review;
- benchmark datasets with documented provenance and licensing.

### Synthetic

Synthetic data must be explicitly labelled and must never be presented as measured project evidence. Synthetic fixtures are appropriate for schemas, tutorials, tests, failure injection, and reviewer examples.

See [`../PUBLIC_DATA_POLICY.md`](../PUBLIC_DATA_POLICY.md) for the authoritative public-data boundary.

## Intended uses

Appropriate uses may include:

- reproducing and evaluating Senior Pomidor data-processing contracts;
- research on state estimation, uncertainty, anomaly handling, replay, decision support, and bounded physical-world AI;
- comparison of deterministic, ML, VLM, or LLM-assisted workflows when a release contains suitable evidence;
- integration examples and interoperability testing;
- transparent reporting of failures, limitations, and negative/null results;
- education or documentation when provenance and limitations are preserved.

## Out-of-scope / prohibited interpretations

Senior Pomidor datasets must not be represented as providing:

- confirmed pathogen identification or plant-disease diagnosis unless a future release explicitly includes independently validated diagnostic ground truth and governance appropriate to that claim;
- clinical, human-health, veterinary, or food-safety diagnosis;
- evidence that a software test proves physical hardware safety or biological efficacy;
- proof of crop-wide, farm-wide, cross-crop, or geographic generalization from a small benchmark deployment;
- authorization for automatic pesticide or biological-treatment decisions;
- ground truth merely because an LLM/VLM generated or a human visually reviewed a label.

See [`NO_DIAGNOSIS_POLICY.md`](NO_DIAGNOSIS_POLICY.md).

## Privacy and release review

Before any dataset release:

- verify the artifact is a deliberate projection, not a raw export;
- remove secrets, SSIDs, IPs, hostnames, paths, logs, stack traces, and unnecessary private identifiers;
- review images for background content and metadata;
- document whether records are measured, observed, derived/inferred, model-generated, human-reviewed, synthetic, anonymized, or sanitized;
- record transformations that affect scientific interpretation;
- verify external-data redistribution rights;
- review partner confidentiality obligations;
- ensure plant-health wording follows the no-diagnosis policy;
- record dataset version, schema versions, and known limitations.

## Limitations and known biases

Current and future data can be affected by:

- a small number of plants and deployment sites;
- tomato-first experimental design;
- sensor calibration, drift, placement, missingness, and failures;
- camera angle, lighting, occlusion, image quality, and background variation;
- environmental confounding between heat, drought, nutrition, infrastructure failure, pests, and disease-like visual symptoms;
- temporal dependence within one growing season;
- interventions/manual actions that may not be fully randomized;
- model and prompt/version dependence for AI-generated observations;
- limited or absent expert/laboratory ground truth for disease claims.

These limitations must travel with downstream benchmark or publication claims.

## Licensing

Dataset licensing is **release-specific** and must be declared in each release README before reuse. Do not infer a data license from the source-code license.

`License: [TO BE DECLARED PER DATASET RELEASE]`

External datasets retain their original licenses/terms and may be referenced rather than redistributed.

## Citation

Until a versioned public research dataset receives a stable release/DOI, use a release-specific citation supplied with that artifact.

`Citation: [TO BE ADDED FOR VERSIONED PUBLIC DATASET RELEASE]`

For the synthetic reviewer sample, cite the repository/path and clearly state that it is synthetic contract documentation, not experimental data.

## Maintenance

Changes that materially alter evidence semantics, public/private boundaries, no-diagnosis policy, or released schema meaning require documentation/version review. Negative findings, known data problems, and corrected labels should be retained or changelogged rather than silently removed when scientifically relevant.
